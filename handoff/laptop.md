# Windows 工作檔：第 10 回合（接力只在必要節點觸發）

更新：2026-10-09 下午｜SilentTalk `copilot-story-mode`｜回報 `laptop-report`｜上一版：開發機 `archive/laptop-2026-10-09-standby.md`（不必讀）

## 為什麼有這一回合

使用者要兩台機器接力，但**只在必要節點觸發，不要常駐迴圈**：不要心跳、不要定時輪詢、不要排程工作，不要產生 log 檔、狀態檔或其他垃圾，沒事不要印東西。這樣連續好幾天開著也不會造成負擔或洗畫面。

開發機那邊已經照這個原則改好：它只等真的在等的東西，沒有待辦就完全不動。開發機需要筆電給它兩個訊號：
- **收件回條：** 拉到新的 `laptop.md` 時推一次。
- **回報：** 照舊推到 `laptop-report`。

這一回合只做筆電這一邊。怎麼接進你現有的監看腳本由你決定，但要符合下面的協定。

## 協定（筆電這一邊）

只有兩個節點，都由事件觸發：

1. **session 開始時**（使用者打開 session，或說「開工」）：
   - 執行 `git pull --ff-only`。
   - 如果 `handoff/laptop.md` 是還沒做完的回合，先推收件回條，再照工作檔做。
2. **一個回合的回報推上去之後：**
   - 再執行一次 `git pull --ff-only`。
   - 工作檔又換了，就推回條、照做；沒換就結束，不要留下來等。

**收件回條**只有這一行：

```
git push -f -q origin HEAD:refs/heads/laptop-received
```

- 它只是把剛拉到的那個 commit 掛到 `laptop-received` 分支，不產生 commit、不寫檔、不印東西。
- 這個分支不會觸發 CI。
- 開發機看到回條包含它交辦的版本，就知道你收到了。沒有回條，就代表你從交辦之後沒開過，開發機也會跟著睡，不會催。

**不要做的事：**
- 常駐或定時迴圈、心跳、Windows 排程工作。
- 寫 log 檔或狀態檔到磁碟或 repo。
- 每次檢查都印訊息。

「這個回合做完了沒」由回報檔判斷：回報開頭寫明回合編號，已經寫「完成」的回合就不要重做。

## 步驟

1. 在 SilentTalk 執行 `git pull --ff-only`，重讀 `AGENTS.md` 和這份。拉不下來就停下回報。
2. 推這一回合的收件回條（上面那一行），然後確認：
   ```
   git ls-remote origin refs/heads/laptop-received
   ```
   - 預期：印出的 sha 等於 `git rev-parse HEAD`。
   - 不相等就重推一次；還是不行，把錯誤訊息寫進回報。
3. 檢查使用者請你設定的監看機制，照上面的協定調整：
   - 有常駐或定時迴圈、排程工作、心跳，就改成上面兩個節點。
   - 你自己建立的排程工作、背景程序或 log 檔，要按確切名稱或 PID 移除。
   - 使用者的檔案和設定不要動。
4. 用開啟 session 時實際會走的路徑試跑一次：
   - 預期：工作檔沒換時，不推送、不寫任何檔案、不印任何東西。
   - 這一回合本身已經示範過「有新工作檔」的情況（第 2 步）。
5. 回報：整份換掉 `handoff/reports/laptop.md`，推到 `laptop-report`，只寫以下幾項：
   - 監看機制最後的形式：用哪種事件觸發、腳本叫什麼名字。
   - 移除了什麼：只寫名稱。
   - 回條是否成功。
   - 試跑結果：寫了幾個檔案、印了幾行。
   - 開頭寫明「第 10 回合：完成」。
6. 之後待命，等出貨回合（開發機還在錄資料和訓練）。

## 不變的規則

- **同一台機器一次只開一個 agent。** 不讀另一台的工作檔，也不讀使用者的對話紀錄。
- **使用者的檔案不能動：** 不動 `.env`、`settings.json`、`personas.json`、`character_state.json`；EdgeAgent 的 `config.json` 只讀。
- **紀錄資料夾：** 只用 `C:\Users\A8fm0\AgentRecords`，只查數量、大小、時間。
- **回報的內容：** 對話內容和角色狀態不進回報。
- **使用者的角色：** 只負責講話、聽和做決定，不做雜事。
- **關程式：** 只用核對過的 PID。
- **推 commit 之後：** 推到 EdgeAgent 或 SilentTalk 之後，等那次 push 的 GitHub 檢查跑完。失敗就修好再結束回合，修不了寫進回報。
